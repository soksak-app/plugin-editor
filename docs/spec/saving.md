# Saving

[한국어](saving.ko.md)

A successful save records the document sent in that write as the saved document. Edits made while the reply is pending remain in the editor and remain modified, including the first save of a blank document. A later save writes those edits and clears the modified state only if the document still equals that write. The version returned by the write is the version used by the next ordinary save. Conflict detection, explicit overwrite, and the original line breaks remain part of this contract.

The editor reports this state through `editor.document` and `context.tab.modified`; the latter is the consumer contract used by the host's close decision. Editor tests use the declared tab interface and controlled files replies, and do not read the host implementation. The host owns the test of its close decision. These tests do not claim native application data loss was reproduced.

Watch reads that overlap another change or save must refresh the current file before applying an older snapshot. A delayed save reply must preserve a newer observed disk version and its conflict indication; an explicit overwrite uses that observed version. Disposing the editor cancels pending file requests, removes its subscription, and prevents a late save, watch or save-place result from updating the tab or starting new work. Request and command failures remain recorded, but a disposed tab receives no new error display.

A completed later save and an explicit reload also supersede older replies. Disk observations, loaded documents and completed saves are tracked separately: a disk observation may show a conflict without replacing the document, while a loaded document must not inherit an older save baseline. The controlled cases delay replies after the file operation takes effect; they verify reply interleavings, not concurrent native file writes or every possible schedule. A superseded reload rejects with `a newer file operation superseded the reload`; its command failure is recorded without replacing the newer operation's tab error. A superseded first save rejects before starting or retrying a write with `a newer save superseded the first save`. An already completed write still returns its own version, but its stale reply does not change the current baseline. Contribution results apply only to the file identity for which they were loaded. Events received before the document opens are retained for a fresh read after initialization. A watch that confirms the saved disk version clears the conflict indication while retaining local edits.

The filesystem integration boundary uses temporary project files, actual operating-system file notifications and a separate process that implements only the declared files request/reply subset. It checks persistence, editing during a paused real write, external-change conflict/reload, stale-read ordering and cleanup through the editor's public commands, status and tab reports. The fixture is healthy during editor mutation checks: restoring the former save-baseline behavior or removing stale-read protection must fail the same integration assertions. This boundary supplements the controlled reply tests and does not import or test another package's implementation.

The integration fixture supports text `read`, `readBytes`, version-checked in-place `write`, file `watch` and `closed` JSONL messages. Write success follows descriptor close and an independent file readback; native notifications may repeat, and the consumer rereads the real bytes. IPC scheduling pauses the real write before its first byte and never fabricates a success response. Held reads keep their original snapshot; held notifications keep the operating-system event and only delay its delivery. The fixture does not cover directory/tree/git operations, metadata/link behavior or partial-write failures. Editor disposal owns request rejection and subscription removal; host-side close owns the close envelope, watcher/process termination and temporary-directory removal. `node scripts/test-filesystem-mutations.mjs` verifies the healthy baseline and isolated editor mutations, requiring the named behavior assertion and successful cleanup even for an intentionally failing test. A loader, build, cancellation or timeout failure is not accepted as mutation evidence.

If the fixture process ends unexpectedly, the host adapter rejects close with the recorded exit cause, cancels every outstanding close wait, and still removes its temporary directory. A fixture-owner fault test verifies this cleanup path separately from the editor mutation evidence.

The shared editor consumer host registers exposed elements through `exposure.element`, as declared by `exposes.element` in the plugin manifest. Filesystem integration and controlled-reply tests use this same host, so they execute against the current exposure contract together.
